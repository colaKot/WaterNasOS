2. 战略前提

2.1 不 1:1 整合

TrailSnap 是「AI 相册 App」（Vue3 + FastAPI + PG/pgvector + 独立 AI 微服务），WaterNasOS 是「NAS 操作系统」（Flutter + Node/Express + SQLite）。 把 TrailSnap 当「照片域的产品化参照系」：抄产品化程度（任务面板、进度可视化、写操作可撤销、叙事层、开放平台），不抄底层 AI 能力（本仓库人脸模型体积 1/50、速度 16×、许可可商用；场景识别 408 类 + 拒识 head + 活动维度，全面领先）。

6. 两个验证动作的实验协议

6.0 铁律（所有 A/B 通用）

⛔ 绝不能拿模型输出改真值、再用同一模型评估。 之前踩过：这样做的 AUC 会被刷成 1.000，实验完全失效。 真值一旦标注，只允许人工修正，且修正记录必须独立留痕。 对比必须用同一评测集、同一评测脚本、同一判据，并做显著性检验（本项目已有 McNemar 精确检验的用法，见 docs/WaterNasOS-场景语义搜索与识别精度方案.md）。

6.1 动作一：多语言 CLIP 文本塔 A/B

问题：本仓库 CLIP 词表 49408 token 里 0 个 CJK ⇒ 中文必须先翻英文，为此维护「512 短语最大匹配 + 有序绑定 + 迟到融合」整套链路。 TrailSnap 用的是多语言蒸馏文本塔 clip-ViT-B-32-multilingual-v1（SiYuan044/clip-ViT-B-32-multilingual-v1-onnx，512 维，61.5MB，int8 后更小）⇒ 中文可直接编码到图像空间。 若它可用，本仓库可省掉整套词表维护成本。

项内容
数据集本仓库已有 150 张人工标注评测集（场景语义方案文档内） + 20~30 条真实中文查询（必须来自真实使用，不要自己编）
对照A = 现有链路（512 短语最大匹配 → 有序绑定 → 无绑定才嵌入最近邻 → 迟到融合 +35%）；B = 多语言塔直编 → 余弦 Top-N
指标Top-5 命中率（主）、MRR、无结果率、单查询耗时
判据B 的 Top-5 ≥ 80% ⇒ 值得切换到直编；< 现有链路 ⇒ 现有词表路线即正确护城河，不必再试
注意蒸馏塔对图像塔有配对要求（必须与同一图像塔配套，否则空间不对齐）；文本 max_length=128

6.2 动作二：PP-OCRv6 vs 当前版本

问题：TrailSnap 用 RapidOCR = PP-OCRv6（det+rec small）+ PP-OCRv4 cls，可能比本仓库现用的代更新。

12.2 动作一：多语言 CLIP 文本塔 A/B —— 直编可用，但结论是「融合」而不是「砍掉词表」

问题：本仓库的中文语义搜索靠「512 短语最大匹配切分 → 有序绑定 → 无绑定才退嵌入最近邻 → 迟到融合」， 维护成本高；TrailSnap 用多语言蒸馏文本塔 clip-ViT-B-32-multilingual-v1，中文可直接编码进图像空间。

做到了什么：

  • 从 hf-mirror.com 取到该模型的 ONNX 文本塔（fp32 514MB）+ tokenizer + 1_Pooling/2_Dense 权重；
  • ⚠️ 该 ONNX 只输出 last_hidden_state（[B,seq,768]），池化与投影在图外 ⇒ 必须自己按 1_Pooling/config.json（mean tokens）与 2_Dense/config.json（768→512、bias=false）接两层， 否则拿到的是 768 维序列而不是 512 维句子向量（第一版就是这么撞的 matmul 维度错）；
  • 零图像推理：两路共用 tool/_tmp/scene_cache/b32/image_embeds.bin（550 行，前 150 行 = 评测集）， 所以差异只来自查询侧编码 —— 这是这次 A/B 最关键的控制变量；
