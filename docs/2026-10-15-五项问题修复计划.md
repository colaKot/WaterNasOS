## 一、人脸：不是阈值问题，是「碎裂 + 烧图」两个 bug

### 1.1 诊断结论（都有实测数据）

**数据底数**：gexuan 库 21591 个文件（18831 图 + 2691 视频），其中 3635 张有人脸行；今天 10:03–13:53 刚全库 reset+重扫过（EdgeFace），数据是新的。

| 疑问 | 实测答案 |
|---|---|
| 阈值太严？ | **不是主因**。已归属照片与新 embedding 对当前原型的 cosine：我 mean 0.711、比比 0.804、街街 0.825，仅 4~5% < 0.45 |
| 组不纯（误合）？ | **没有**。390 个多样本组的组内纯度 385 个 ≥0.45；三人组间相似度仅 0.06~0.15，分得很开 |
| 那问题是什么？ | **① 同一人裂成了几百个组；② 推理失败的照片被永久标记完成（烧图）** |

**① 碎裂**：与「我」组均值相似度 ≥0.60 的组有 **271 个**——其中 **246 个不足 10 张**，被人脸页默认显示门槛（`ai_face_min_show_count=10`）藏掉，用户看不到也合不了。按 ≥0.45 全并的应得数量（gexuan 库内）：

| 人物 | 现在 | 全并后 | 涉及组数 |
|---|---|---|---|
| 我 | 329 | **~731** | 188 |
| 比比 | 110 | **~1170** | 491 |
| 街街 | 111 | **~1154** | 547 |

根因：二次合并太弱——`SECOND_MERGE_MIN_FACE_COUNT=3`（1~2 张的碎片永不参与）、每轮维护最多并 20 对（`SECOND_MERGE_MAX`）、互为最近邻+三档门槛。认领端 0.45+质量惩罚+0.04 裕度对年轻/非典型原型偏严，新组一旦建出来就再也合不回去。

**② 烧图（更严重）**：`faceWorker.processBatch` 里推理失败走 `markIndexDone` ⇒ `gen_faces=1` 永不重扫。服务端错误日志实证 **1198 条** `face infer failed`（19:01–19:02 两分钟内线程池系统性死亡，bare "Error"），另有一次更早的失败潮（日志已轮转删掉）。抽样 250 张「无人脸」照片用同一模型重跑：**58 张能检出人脸（置信度 82~88），其中 39 张与三个已知人物相似度 ≥0.45**，肉眼抽查确认是真人（如 2013 年麦理浩径裸上身半身照，与「我」0.817）。按此比例估算：**gexuan 库约 2300 张、bibi 库约 8000 张真人脸照片被烧掉**——这就是「2000 张只剩 300 多」的主要缺口。

（附：`qualityScore=检测置信度×100` 不是清晰度门，`DET_SCORE_THRESH=0.8` 才是真门；实测无人脸照片里能检出的脸置信度全部 ≥82，所以「降低质量门」对找回照片没用，别走这条路。）

### 1.2 修复方案

**F1 修烧图 bug**（`faceWorker.js`，既有文件可热更）
- 推理失败不再 `markIndexDone`：重试 3 次（间隔退避）仍失败则**保留 `gen_faces=0`** 下轮再来，并打错误日志带真实原因；
- 线程池连续失败 N 次 ⇒ 主动 `terminate` 重建线程；重建仍失败 ⇒ 回落 coordinator 内联推理（现有机制加触发条件）；
- 单张推理失败与「线程池死亡」分开计数，后者告警级日志。

**F2 存量补扫**（新增动作，走已有 `rescanFaces` 的缩小版）
- 对「当前用户可见路径内、`gen_faces=1` 但 f2h 无行」的照片置 `gen_faces=0`，后台 worker 自动重扫；
- 预计耗时：gexuan 库 ~1.8 万张 × 0.2s（3 线程）≈ **1 小时**；含 bibi 全库 ~5.7 万张 ≈ **3.5 小时**。建议只勾自己的库先跑。

**F3 碎片自动归并**（`faceWorker.js` 维护任务 + 一次性全库任务）
- 维护参数：`SECOND_MERGE_MIN_FACE_COUNT` 3→**1**、`SECOND_MERGE_MAX` 20→**200**、`MAINTENANCE_FACE_LIMIT` 200→**500**；
- 新增「合并相似人物」全库任务（管理员在 AI 设置页触发）：按**组样本均值**相似度 ≥ **0.60** + 与第二名裕度 ≥0.05 + 互为最近邻才并；
- 安全依据：实测三人组间 0.06~0.15；与「我」≥0.60 的 271 个组里**只有 1 个已命名且就是「我」自己**；两侧都已命名的组**不自动并**（只提示人工）；
- 预期：我 329→~731、比比 110→~1170、街街 111→~1154（gexuan 库内，不含 F2 补扫增量）。

**F4 UI 放开可见性**
- `ai_face_min_show_count` 默认 10→**3**（或人脸页加「显示全部人物」开关，改动小推荐开关）；
- 人脸相册多选态补「移动到…」批量入口（服务端 `movePhotoToFace` 已存在，只差前端按钮）——这是修存量错组的正门。

**F5 验证**：归并+补扫后重跑 `tool/_diag_face_split.py` / `_diag_face_purity.py`，对比三人照片数与组数；抽样 100 张人工看图复核纯度。

## 二、时间轴语义搜索：「夕阳下的沙滩」直接出图

### 2.1 现状（链路是通的，只是没接线）

- 语义搜索**已全部落地**：`placesQuery`（中文→512 短语最大匹配→有序绑定→迟到融合）+ 408 个标签 + `query_lexicon.json`/`query_embeds.bin` 都在 dist_v22 里；
- 但**只接到了 AI 场景页**。时间轴搜索（`photoTimeLineService.js` 215–251 行）只有：路径/文件名/相机 LIKE + OCR + 场景标签**子串** LIKE ⇒「夕阳下的沙滩」逐字匹配任何标签都失败 ⇒ 空；
- 实测词表解析正确：「夕阳下的沙滩」→ 归一化「夕阳下的海滩」→ **日落 + 海滩**两个标签；
- 数据也在：gexuan 库 海滩 567 张、日落 335 张，`alt_labels`（JSON 多标签）另覆盖 495 张。

### 2.2 方案（推荐 A+B，C 作为二期可选）

**A. 接线（必须，服务端既有文件可热更）**
- `photoTimeLineService.js` 搜索块：调 `placesQuery.analyze(search)` 拿到标签集合，追加 OR 条件——`place_name IN (标签)` OR `alt_place_name IN (标签)` OR `alt_labels` JSON 含标签；
- 与现有字面匹配取并集；开关沿用 `ai_place_enable`；
- 搜索框下方复用场景页已有的「已识别：日落 · 海滩」提示条（13 语言键已存在，**零新增 key**）。

**B. 排序优化（推荐一起做）**
- 多标签命中排前：一条轻量聚合查询算 `file_hash → 命中标签数`，主查询按「命中数 DESC, 时间 DESC」排——「夕阳下的沙滩」先出真正又夕又沙的，再出只命中一个的；
- 字面命中（文件名/OCR）保持原时间序，混排时语义命中优先。

**C. 二期可选：SigLIP2 照片级向量检索**（回答你「不怕麻烦不怕下载」）
- 现状瓶颈是 408 个标签装不下「两只狗在草地上跑」这类描述；上照片级 embedding 后任意自然语言直接检索；
- 成本：SigLIP2 base 双塔**已在本地**（活动维度在用），6.75 万张算 embedding ≈ 1 小时一次性，存储 138MB（float32）或 34MB（int8）；查询侧 512 短语嵌入用 SigLIP2 文本塔重建（构建期一次）；
- 风险：检索精度依赖模型本身，CLIP 系对细粒度场景描述一般够用但不神奇；工作量约 2~3 天（新表 + worker + 检索链路 + 评测集）。
- 建议：先把 A+B 上线用两周，不够再上 C。

## 四、文档阅读器：不用造轮子，项目里已经有一个

### 4.1 发现

`electron_server/package.json` 已依赖 **`@anohanafes/offline-document-viewer@1.0.1`**（MIT 协议，GitHub: anohanafes/offline-document-viewer）：
- 支持 **PDF / DOCX / PPTX / XLSX / CSV**（底层 pdf.js + mammoth.js + SheetJS，全部本地打包，完全离线）；
- **已经在 asar 里随包发布**（dist_v19~v22 都有），但 `src/` 零引用——加了依赖没接线；
- TXT 不在其列表，但纯文本 `<pre>` 渲染一行搞定，可顺带做。

### 4.2 集成方案（推荐）

- **服务端**：`app.js` 加一个静态路由（如 `/docview/`）把该目录挂出来（可免登录或走现有 token 参数，参照 `/wallpaper` 的 `authenticateJWT` 写法）；加一个 20 行的 launcher 页接收 `?url=<文件URL>` 调起阅读器；
- **客户端**：文件列表/文件预览的「打开」按钮，用现成的 `webview_flutter` 模式（照抄 `legal_document_opener.dart`：桌面/网页开系统浏览器标签，移动端开应用内 WebView）打开 launcher URL；
- 工作量：服务端 ~50 行、客户端 ~80 行，**无新增依赖、无模型下载**。

### 4.3 为什么不用别的

OnlyOffice Docs / Collabora Online / KKFileView 都能干，但都要 Docker 或 Java 服务——你禁 Docker、要离线，直接排除。内置这个离线阅读器是唯一契合路线。
