# 场景语义搜索与识别精度方案

> 2026-10-14 · 回应铁柱两条诉求：
> 「**我想要能通过语义来搜索，不是现在这样只能搜出场景，比如我想要 夕阳下的海滩**」
> 「**而且现在场景识别也还是不准。你看看有什么方案**」
>
> 本文所有数字都是本机实测（150 张人工标注集 + 400 张库样本），
> 复现脚本见第 6 节。**不要凭直觉改标签表** —— 第 2.6 节的对照实验证明，
> 「往标签表里加好东西」这一步本身就会掉准确率。

---

## 1. 结论速览

| 问题 | 结论 |
|---|---|
| 语义搜索能不能做 | **能，已经跑通并落地**（解析层 + 服务端接口 + 前端接入 + 真实库验证 27/27） |
| 代价 | **零新增模型**（不发布 61.5MB 文本塔），运行时只多 **1MB** 词表+嵌入 |
| 「夕阳下的海滩」 | 现状只能找到「海滩」⇒ 现在切出 **日落 + 海滩** 两个标签 |
| 中文能不能直接编码 | **不能**：CLIP 词表 49408 个 token 里 **0 个含中文**，直查全是噪声 |
| 加标签能不能提准确率 | **加「属性类」持平（无损，Top-1 47.4%→47.4%）**；**加「主体/季节类」显著掉点**（40.0%，p=0.0156） |
| 换更强视觉塔能不能提准确率 | **量不出来**：b16 明显更差（38.9%），L/14 略低（45.3%）且 **p=0.8450 不显著**、Top-3 持平。**不是杠杆**（详见 2.7） |
| 识别不准的根治手段 | ① 多标签入库（Top-3 存全）② 提示词集成 ③ **可判性 head 做「我不知道」出口**（第 8 节，已实测达标）④ 换塔已证伪 |
| 「我不知道」出口能不能做 | **能做，但必须训练**：现有 weight 门控**方向是反的**（−24.6pp）；6 种零样本判据**全部不达标**；训一个 512 维二分类 head ⇒ **CV AUC 0.807**，误伤 4.2% 时能拦下 36.4% 的「不该判场景」照片（第 8 节） |
| 「我不知道」出口落地没 | ✅ **已落地**（dist_v19，2026-10-15）：3 个既有文件 + 1 个 head 产物；真实库抽样 **10.8% 不给场景标签**；**老数据迁移已完成**（64136 → 59130 行，8.10） |
| 扩标注值不值 | **只对「可判性 head」值得**（训场景分类器已证伪）。且曲线很平（n=60→0.76，n=150→0.80）⇒ 重点不是堆量，是**补现在只有 1~6 张的类**（户外合影/室内聚会/团队合影） |
| 扩标注怎么配合 | 已产出**可交互标注页**（8.11 / 8.13）：四组挑样 **144 张**，浏览器里点「该给/不该给」，导出 JSON 直接重训。第三轮已改**盲标**（不显示 head 判定与分数）**+ 口径写进页面 + 每批 ≤40 张** —— 前两轮分别栽在「刷新丢标注」和「锚定」，这两处都有自测把守 |
| 第二轮标注能用吗 | ❌ **不能用**（8.12）：抽核 25 张发现约 20 张与页面口径矛盾（人像/截屏标「该给」、山景标「不该给」）⇒ **保留 v1 head 不重训**；head 在这些硬样本上的判定经人工看图验证几乎全对 |
| 第三轮标注（盲标）能用吗 | ✅ **能用**（8.14）：144 张全标（19 该给 / 125 不该给），抽核 9 张 **8 张一致**，唯一争议是「薰衣草田人像」属定义边缘；dry 重训 CV AUC **0.807 → 0.913** |
| 婚礼/游泳/跑步场景会识别吗 | **婚礼·游泳 ✅ 词表里有**（婚礼现场 / 游泳馆 / 室内外游泳池 / 天然泳池）；**「跑步」词表里没有**，「跑道」的英文提示词其实是**机场跑道**（8.14）。门控对这些类是**几乎零误杀**：泳池 0~0.4%、运动场 0%、健身房 2.2%；只有「以人为主体」的婚礼现场 28%、演出场馆 24%、服装店 45% 会被拦下 |
| 动作/情绪标签能不能加 | ❌ **零样本不通**（8.15）：词表草案 47 类（`tool/_act_tags.txt`）+ 15 张人工真值 ⇒ CLIP 零样本 Top-1 **0/15**、Top-3 2/15；Top1−Top5 间距仅 0.025、Top-1 分数全挤在 0.226~0.285，**连静物都被判成「切蛋糕」**。要做得接**专用模型**（Kinetics 动作 / FER 表情）；自训 head 需上万标注，不推荐 |
| 专用模型行不行（已下载实测） | **分三种**（8.16）：① 15 类动作模型 apache-2.0 ✅许可但**不能用**（闭集无拒答，整图 0/15）；② 400 类 TimeSformer **定性最像样**（过溪 100%/瑜伽 97%/用餐 69%）但 **cc-by-nc-4.0 ⛔不能商用**；③ 7 类表情 apache-2.0 ✅、大笑→happy 99%，但微笑→angry 48%，**n=3 不敢下结论**。模型已存在 `_toolchain\models\_dl\` |
| ⭐ **SigLIP 2 开放词汇** | ✅ **这是正解**（8.17）：同一套 15 张真值，SigLIP 2 base-224 **Top-1 60% / Top-3 86.7%**（英文候选），静物拒识 3/3，**相近活动区分 5/5**（badminton>volleyball>tennis、hiking≫cycling>swimming）——CLIP 零样本和闭集模型都是 0/15。**apache-2.0 ✅**，运行时**只发视觉塔 52MB**（q4f16），与现有 CLIP（85MB）同量级。⚠️中文明显弱于英文（Top-1 60%→40%、拒识 3/3→1/3）⇒ **中文翻译层不能砍** |
| 上更大的模型有用吗 | ❌ **没用，别上**（8.18）：扩到 26 张真值，**so400m-384（fp16 817MB）英文 Top-1 与 base-224（52MB）持平（16/26）**，只中文 50%→65%；代价 **98ms → 2075ms（21×）**，6 万张从 1.6h 变 34.6h。三个模型在 9/11 个错误上「一起错」⇒ **瓶颈不在容量** |
| 拒识该怎么做 | ⭐ **用事后阈值，别用锚点候选**（8.18.4 → **8.19/8.20 定稿**）：`unrelated` 当候选参选会变成 hub（抢 11/26、错 7 次）；改成「先只排活动候选 → 再用阈值判有没有活动」后，**英文 AUC 0.966，τ≈0.078，5.5% 误伤下拦下 87.4%**（负样本 196 张）。⚠️8.18.4 那句「完全不重叠」是**只有 5 张负样本的假象**。中文弱得多（AUC 0.817 / 拦 38.3%）⇒ **拒识也必须走英文** |
| 拒识的**根因** | ⭐ **图文模型匹配「物体」，不匹配「动作」**（8.20.4）：真·无人的「湖中小船 / 桌面棋盘 / 书本」照样匹配到 kayaking / playing cards ⇒ 是编码器的结构性局限，**阈值有天花板**。加「照片里有没有人」的门方向对，但**用文本提示实现无效**（margin AUC 仅 0.627；门控+阈值拦 96% 但**只留 52% 正样本**）⇒ **需要一个真正的人物检测器**（Apache-2.0 的 SSD-MobileNet / RT-DETR 候选） |
| ⭐ **人物门控（已落地验证）** | ✅ **有效**（8.21）：用 `facebook/detr-resnet-50`（**apache-2.0**，ONNX fp16 79.8MB / q4f16 56MB，386ms/张）。**宽松档「门控+阈值」把拦下率从 87.4% → 90.0%，正样本只掉 0.2pp**；AUC 活动分 0.966 / 人物概率 0.869。成本可控：只在「活动分 ∈ [τ,1.3τ)」的不确定带里跑门控，**实测占 12.0% 照片**。⚠️剩下的 19 张「失败」**personProb 全是 1.000**（其实有人）⇒ **已撞到标签天花板**，再提升要靠收紧「无活动」的标注定义，不是换模型 |
| ⭐ **拒识指标修正 + q4f16 定稿** | ✅（8.22）：8.21.3 说的「19 张失败」是**低估** —— `personProb ≥ 0.999` 的「无活动」照片实为 **71/196 = 36%**，人工核对后 **57 张其实是人物照**（从负样本剔除）。⚠️ **⛔不能用门控改标签再拿门控评估**（会把 AUC 刷成 1.000）。人工修正后：**AUC 活动分 0.991 / 人物 0.977；宽松档拦下 96.6%（+3.0pp）正样本仅掉 0.2pp**；不确定带降到 **9.4%**。DETR **q4f16 与 fp16 门控结论逐位一致**（Δ中位 0.0028）⇒ **用 q4f16 省 24MB** |
| 活动维度集成 | ✅ **已落地**（8.23）：`dist_v20` 整包重打完成（2.0GB，+109MB）。具体设计见 8.22.7，落地记录与 **2 个真 bug**（personProb 未归一化误杀正样本 / `onConflict().ignore()` 在 better-sqlite3 下返回 `[undefined]` 致计数虚高）见 8.23。4 组验证全过（e2e 160 张 / 建表 14 / 接线 30 / 打包产物 15）。⏭ 全库重扫需手动起服务端。原方案要点：新增 SigLIP 视觉塔 52MB + DETR q4f16 56MB = **108MB**（全部 apache-2.0）；活动标签写**独立列** `act_name/act_score/act_alt`，与 408 类场景**不共享标签空间**；实测只有 9.4% 照片需跑 DETR，全库重扫约 1.7h |
| 哪些场景值得投入 | ⚠️ **高频 ≠ 常见**（8.20.1）：Top-30 里的 `沙漠`(1623)/`室内溜冰场`(1511)/`游戏厅`(949)/`木筏`(759)/`消防站`(709) 都是模型在中文照片上**乱输出的西方类** ⇒ 不能拿类频次当「国内常见度」。真正该忽略的是 `冰球馆`/`马术竞技场`/`斗牛场`；该补的是 `钓鱼`/`烧烤`/`露营`/`打牌`/`健身`（已加，候选 25→32） |

## 2. 实测证据

### 2.1 前提：CLIP 是纯英文模型

```
vocab.json: 49408 tokens, 含 CJK 的 token = 0
模型: Xenova/clip-vit-base-patch32（vision 85MB / text 61.5MB，均 int8 量化）
```

### 2.2 编码链路完全可复现（这一步是关键前提）

用仓内 `src/utils/clipTokenizer.js` + 文本塔，对 `scene_tags.txt` 里的英文提示词重新编码，
与已发布的 `text_embeds.bin` 对应行比余弦：

```
海滩  "a photo of a beach."          cos(自算, 已发布) = 1.00000
天空  "a photo of a sky."            cos = 1.00000
厨房  "a photo of a kitchen."        cos = 1.00000
病房  "a photo of a hospital room."  cos = 1.00000
```

⇒ 构建期重建标签嵌入是**安全的、可重复的**，可以放心扩词表。

### 2.3 英文自然语言查询 → 标签：有效

| 查询 | top-1 | top-2 / top-3 |
|---|---|---|
| `a photo of a beach at sunset.` | **海滩 0.951** | 海滨小屋 0.934 / 海岸 0.920 |
| `a photo of a snowy mountain.` | **雪山 0.994** | 山 0.971 / 雪原 0.953 |
| `a photo of a plate of food on a table.` | **食物特写 0.963** | 聚餐桌 0.950 / 美食广场 0.933 |
| `a photo of a cat sleeping on a sofa.` | 地下墓穴 0.841 ❌ | 客厅 0.821 / 卧室 0.810 |

最后一行是**要害**：标签空间里没有「猫」，最近邻就变成任意的「地下墓穴」。

### 2.4 中文直接编码：退化

```
「夕阳下的海滩」→ 壁龛 0.908  驾驶舱 0.907  小岛 0.906  废品场 0.904
「雪景」        → 废品场 0.953  小岛 0.953  壁龛 0.952  果园 0.951
```

余弦全挤在 0.90~0.95 且结果与语义无关 ⇒ **必须走「中文 → 英文提示词」的映射**。
这就是查询词表（`scene_query_lexicon.txt`）存在的根本原因。

### 2.5 组合语义：短语加权平均 ≈ 整句真实编码

用户会自由拼词（「雨天的山村」），穷举整句不可能。实测「短语嵌入加权平均」
与「整句真实编码」的余弦：

```
a photo of a beach at sunset.        → 0.9755   top6 重合 3/6
a photo of a snowy mountain at sunrise → 0.9734   top6 重合 4/6
a photo of a rainy street at night.  → 0.9763   top6 重合 2/6
a photo of a village in autumn.      → 0.9707   top6 重合 3/6
a photo of a dog on a beach.         → 0.9474   top6 重合 3/6
```

⚠️ 组合向量会**压平分数**（无关标签全挤到 0.95+），所以运行时**不能先平均再比对**，
必须「每个短语各自投票 + 被多个短语同时命中的标签加成」（`placesQuery` 里的迟到融合）。

### 2.6 ⭐ 加标签的代价：A/B 对照（本方案最重要的一张表）

**担心**：`placesFusion` 的两处归一化都是**跨类**的（`zscoreAcrossClasses` 减全体均值、
softmax 分母是全体指数和），多一个类别，旧类别的票就被稀释。

**做法**：图像嵌入与标签表无关 ⇒ 缓存 150 张评测集的图像嵌入 + Places365 logits，
换标签表只重做点积。标定用另外 400 张（与评测集不相交），口径与既有
`tool/_scene_eval.js` 一字不差（ACCEPT 表直接从源码抽取，避免标注漂移）。

| 变体 | 标签数 | Top-1（95 张可评） | Top-3 | McNemar vs 现状 |
|---|---|---|---|---|
| **A 现状** | 381 | **47.4%** | **60.0%** | — |
| B +时间/光照/天气 | 400 | **47.4%** | 58.9% | 0 换 0，**p=1.00 不显著（无损）** |
| C +视觉风格（B+I） | 408 | **47.4%** | 57.9% | 0 换 0，p=1.00 / Top-3 p=0.50 |
| D +季节植被 | 410 | 44.2% | 56.8% | −3 换 0，p=0.25 |
| E 全部 61 个 | 442 | **40.0%** | 52.6% | **−7 换 0，p=0.0156 显著变差** |

E（全量）掉的那 7 张，一眼就能看出病根：

```
gt=园      现状 公园   → 全量 樱花      （樱花抢公园）
gt=自:农田  现状 农田   → 全量 花        （花抢农田）
gt=商:餐饮店 现状 面包店 → 全量 蛋糕      （蛋糕抢面包店）
gt=自:山水  现状 雪山   → 全量 冬天      （冬天抢雪山）
```

主标签分布里 **`宝宝×10` 直接成了新的万金油** —— 与 `placesFusion` 头注释记录的
「病房/荒漠/美容院/育婴室」是**同一个病**：泛化标签 = 新 hub。

**⇒ 结论：泛化的「主体/人物」类标签（宝宝/合影/自拍/猫/狗/花/美食/蛋糕/樱花…）
绝对不能和场景标签放在同一个 softmax 竞争空间里。**

**✅ 已执行**：A+B+I 共 27 个属性标签已并入正式 `scene_tags.txt`（381 → **408**），
`text_embeds.bin` 已重建（408×512，835,584 字节）。并入后重跑评测，
`A 现状408(已发布)` = **Top-1 47.4% / Top-3 57.9%**，与并入前的内存版 C 变体
一字不差 ⇒ 落盘产物 = 被评测的变体，数字可以互相背书。
新增 27 个标签在评测集 top3 里被触发了 **12 个**（黑白×3 夜景×3 逆光×2 雾天×2 航拍×2 …），
说明这批标签在真实照片上确实会命中，不是纸面标签。

### 2.7 ⭐ 换更大的视觉塔：实测把它证伪了

「换更强的视觉塔是最大杠杆」这个直觉，**实测不成立**。用户授权下载后（走 `hf-mirror.com`，
huggingface.co 直连与代理 127.0.0.1:21578 均超时），三个**同族**模型用各自视觉塔跑同一批
550 张图（图像嵌入缓存各自独立），标签空间统一为已并入后的 408：

| 标签空间 | 标签数 | Top-1（95 可评） | Top-3 | McNemar vs b32 |
|---|---|---|---|---|
| **b32（ViT-B/32，现状）** | 408 | **47.4%** | **57.9%** | — |
| b16（ViT-B/16） | 408 | 38.9% | 54.7% | 独对 13 / 独错 5，p=0.0963 不显著 |
| l14（ViT-L/14，768 维） | 408 | 45.3% | **57.9%** | 独对 14 / 独错 12，**p=0.8450 不显著** |

- b32 精确复现 47.4%/57.9% ⇒ **评测管线自身可信**（换塔后标签嵌入也是同族重建的）。
- **b16 明显更差**（−8.5pp）：patch 变细但没有全局结构，在这批场景图上反而更糟。
- **L/14 不显著**：Top-1 低 2.1pp、Top-3 持平，McNemar 完全对称（14 换 12）。
  唯一可说的收益是 **hub 被压平**（主标签 `婚礼现场` 从 ×10 降到 ×5，分布更分散），
  但那是「更不集中」不等于「更准」。
- 代价还不小：视觉塔 85MB → 292.8MB（+207.8MB），推理 ~145ms/张 → ~320ms/张，
  而且 **CLIP 目录不在 `remoteAssetsManager` 的三个 bundleId（faces/ppocrv3/places365）里**，
  要么包体加 208MB，要么为它新增一套远端资源清单。

**⇒ 结论：不换塔。** 留着这套基础设施（`tool/_scene_models.js` + `_dl_clip_bigger.py`
+ 已下载的 b16/l14 文本塔与视觉塔），等评测集扩到能分辨 2~3pp 差异时再回来判断。
现有 150 张评测集**内容偏场景**（缺日落/雪山/猫），本来就不适合给"换塔"投票。

## 3. 方案

### 3.1 语义搜索（已落地，可热更/需整包）

链路：

```
中文查询
  → 查询词表最大匹配切分（512 条短语；有序绑定 猫|宠物特写、雪景|雪原）
  → 每个短语取「构建期预算好的 CLIP 文本嵌入」
  → 绑定标签为权威映射；无绑定的氛围词才退回嵌入最近邻
  → 迟到融合：score(标签) = Σ 短语权重 × 该短语给的分，被多短语命中的加成 35%
  → 查 photo_places / photo_places2filehash（沿用现有可见性口径）
```

实测解析效果（`现状` = 现在的标签名子串匹配能搜到的）：

| 查询 | 切分 | 命中标签 | 现状 |
|---|---|---|---|
| 夕阳下的海滩 | 夕阳→**日落** ＋ 海滩 | 日落、海滩 | 只有 海滩 |

## 7. 「自己训练一个 head」值不值得做（已实测，别再凭感觉试）

**结论先行：在当前标注量下不值得，而且训了比不训更差。** 真正卡住精度的不是模型容量，
是**标注数据量**和**任务定义**这两件事 —— 两者都不是换模型能解决的。

做法：冻结 CLIP 图像嵌入（512 维，L2 归一化）→ 岭回归到标签目标 → 5 折 CV × 重复 20 次。
脚本 `tool/_scene_train_probe.js`（纯 JS，**零下载**；用对偶解 `Xᵀ(XXᵀ+λI)⁻¹Y`，
n<d 时比 `(XᵀX+λI)⁻¹` 快 3 个数量级）。样本 = 95 张可评。

| 口径 | 类别数 | 每类样本 | CV Top-1 | CV Top-3 |
|---|---|---|---|---|
| A 宽松多标签（= 要输出任意 408 标签，**最接近真实部署**） | 186 | 0.51 | **43.5%** | 56.2% |
| B/C/D 单正类（类别空间 26 / 186 / 408，三者结果**完全相同**） | — | 3.65 / 0.51 / 0.23 | **48.3%** | **65.9%** |
| 零样本融合基线（现状） | 408 | — | 47.4% | 57.9% |

**A 口径（唯一的真实部署口径）训了比零样本还差 3.9pp Top-1。**
B/C/D 那个 +8.0pp Top-3 是**假象**，诊断证据：

```
D 行（408 类空间，单次 CV 留出预测 95 张）：
  Top-1 落在「训练集见过的 26 类」内的比例：95/95 = 100.0%
  预测出来的不同标签只有 14 个
```

类别空间从 26 扩到 408 却完全不掉分，是因为**只有那 26 列有正样本**，其余列目标全 0 ⇒ 分数被压平，
模型根本不会输出它们。真实照片有几百种场景 ⇒ 未见过类别的照片会被**强行塞进这 14 类之一** ——
与 memory 里记的「hub=宝宝×10 / 病房×1224」是同一种病。

其他证据：

- 训练集内自评 **76.8%** vs CV **43.5%** ⇒ 95K 参数 vs 95 样本，纯过拟合。
- 学习曲线（λ=0.001）：19 张 23.4% → 38 张 33.1% → 57 张 37.0% → 76 张 39.2%，**始终低于 47.4%，没有交叉**。
- 粗估（外推，误差大）：追平零样本约需 **150~300 张**标注；稳定 +5pp 以上约 **500~1000 张**；
  要覆盖长尾（95 张仅覆盖 26 类，而标签空间有 408 类）需 **3000+ 张**。

### 7.1 训练救不了的那部分：1/3 的照片根本没有「场景」这个答案

`tool/_scene_gt_150.csv` 150 张里 **55 张被标为「不可评」**，其中
**人像 23 + 合影 13 + 静物 9 = 45 张（占 82%）**。

⇒ 「场景识别还是不准」有一部分**根本不是模型问题**，是**任务定义**问题：
拿场景分类器去判人像 / 合影 / 静物，换塔、训练、调参都救不了。
**解药是主体/人物类独立 head（可复用人脸模块已有的检测能力），不是继续抠场景精度。**

另注：评测表里「出标签 100.0%」⇒ `unknown` 门控**没有真正拦下任何一张**，系统从不说「我不知道」。

### 7.3 精度提升方案清单（按「确定性收益 / 成本」排序）

**第一梯队 —— 零训练、收益有数字支撑：**

1. **候选数从 2 扩到 3** ⇒ **+3.2pp**。
   实测 Top-1 **47.4%** / Top-2 **54.7%** / Top-3 **57.9%**；表里现在存 primary + 1 个 `alt_place_name`
   = 2 个候选，所以扩到第 3 个候选的**净增量 = 57.9 − 54.7 = +3.2pp**（精确、可落地）。
   ⚠️ 代价：每张照片会多进一个相册（召回↑、纯度↓），要产品侧拍板。
2. **加真正的「不可评」出口**。现状 100% 出标签 ⇒ 人像/合影/静物必然被塞个错场景。
   让这批照片**不给场景标签**，比给个错的强得多。直接命中用户痛点，成本低。
   ⚠️ **2026-10-15 更新：实现路径已改写**。原设想的「提高 `lowThreshold`」被实测推翻
   （方向是反的，见第 8 节）。正确做法是**离线训一个 512 维「可判性 head」**，见 8.7。
3. **标定样本量 200 → 800**。`zscoreAcrossClasses` 的均值/标准差估计更稳，成本极低（标定阶段多跑几张图）。
4. **提示词集成扩面**。现在只给 A/B/I 27 个新标签配了多提示词；给高频混淆对
   （公园/植物园、客厅/儿童房、面包店/餐厅…）各补第二三条，零风险。

**第二梯队 —— 要开发，且必须先有标注：**

5. **主体/人物类独立 head**（人脸/人体检测 + 多标签 sigmoid，与场景空间解耦）。
   这才是符合数据分布的方向（见 7.1），且人脸模块已有检测能力可复用。
6. **重排器**（在 Places365 top-k ∪ CLIP top-k 上训小模型）。需要千级标注。

**第三梯队 —— 成本高、收益已被证伪或不确定：**

7. 换更大视觉塔 ⇒ **已实测证伪**（见 2.7：b16 更差、L/14 不显著）。
8. 微调 image encoder（LoRA）⇒ 需 GPU + 3000 张标注，且收益被 7.1 的任务定义问题压着。
9. 从零训模型 ⇒ 无 GPU、无数据，不现实。

### 8.1 现有 weight 门控方向是反的（`tool/_scene_gate_probe.js`）

库里 `photo_places2filehash.place_status` 确实有 `confident|ambiguous|unknown` 三态，
真实库分布 confident 32363 / ambiguous 20707 / unknown 11066（unknown 占 17.3%）。
但把它按人工标注分组一看：

| 状态 | 张数 | 其中可评 | 可评组 Top-1 |
|---|---|---|---|
| confident | 60 | 32 | **50.0%** |
| ambiguous | 53 | 31 | **54.8%** |
| unknown | 37 | 32 | 37.5% |

| 人工标注 | 张数 | unknown 占比 | 非 confident 占比 |
|---|---|---|---|
| 可评 | 95 | 33.7% | 66.3% |
| 不可评 | 55 | **9.1%** | 49.1% |
| ⇒ 差值 | | **−24.6pp** | −17.2pp |

- **方向完全反了**：该被拦的「不可评」反而更少被打成 unknown。
- **confident 组 Top-1 反而低于 ambiguous 组**（50.0% vs 54.8%）⇒ 门控连「自己判得准不准」都没抓住。
- `lowThreshold` 从 0.10 扫到 0.25，**所有档位**分离度都是 **−16 ~ −25pp**。

**为什么**：人像照片的「背景像某个室内场景」⇒ 权重反而高 ⇒ 被**自信地**判成
美容院 / 服装店 / 婚礼现场 / 化学实验室。实测不可评样本的错判：
人像→美容院×2/糖果店/服装店（confident 3/9）；夜景人像→婚礼现场×3；
户外合影→校园/幼儿园教室/黑白；食物特写→面包店×2/水族馆；室内人像→化学实验室/海洋球池。

**⇒ 结论：不能靠调阈值，必须换判据。**

### 8.2 六种判据横向对比（全部实测）

| CLIP 非场景锚点 `max-margin` | +23.6pp | **20.0%** | — | 代价太大 |

### 8.3 为什么零样本判据全废

`tool/_scene_nonscene_probe.js` 给标签空间加了一组「非场景锚点」英文提示词
（人像 / 合影 / 画作插画 / 纯物件），让它们与 408 个场景标签同台竞争。
逐样本诊断暴露了根因：

```
[人像]        场景 top3: 塔寺 0.2306 | 温泉 0.2287 | 瑞士小屋 0.2274
              锚点     : 非:人像 0.2114 | 非:纯物件 0.2114 | ...
[户外合影]    场景 top3: 校园 0.2616 | 游乐园 0.2554 | 草坪 0.2522
              锚点     : 非:合影 0.2511 | ...
```

- 锚点分数只差场景最高分 **0.001 ~ 0.02**（户外合影那张只差 **0.0010**）。
- 但**「取 408 个候选的最大值」天然有偏**（N=408 vs N=4，max 期望高约 1.8σ）⇒ 锚点永远压不过。
- 而 z-score 校正掉这个偏置后：`zScene` 恒 ≈3.2、`zOther` 只有 ≈1.3 ⇒ **完全没有可分信号**。
- 换到「场景归属确定性」（场景内部 top1−top2 / 分布熵）也一样：真场景与假场景在
  B/32 嵌入空间里**没有单变量可分性**，只能靠多变量线性组合。

**⇒ 这就是必须训练 head 的原因。零样本单变量判据在这条路上是死的。**

### 8.4 训练「可判性 head」达标（`tool/_scene_nonscene_probe.js` 第 8 节）

做法：冻结 CLIP 图像嵌入（512 维，**已 L2 归一**，实测 `|x|=1.0000`）→ 岭回归到 ±1 二分类目标
→ 对偶解 `Xᵀ(XXᵀ+λI)⁻¹Y`（n<d 时快 3 个数量级）→ 5 折 CV × 20 次重复。
⚠️ 这与 7 节的「训场景分类器」是**不同问题**：二分类、2 个输出，样本需求远低于 408 类。

```
λ=0.01   CV AUC = 0.7838 ± 0.0201
λ=0.1    CV AUC = 0.8068 ± 0.0175
λ=1      CV AUC = 0.8074 ± 0.0154   ← 最优
λ=10     CV AUC = 0.7512 ± 0.0225
λ=100    CV AUC = 0.6401 ± 0.0624
⇒ bootstrap 95% CI（2000 次重采样）：AUC ∈ [0.748, 0.873]   （下界远高于 0.5 ⇒ 信号真实）
```

工作点（trade-off 由产品侧拍板）：

| 档位 | 阈值 | 可评误伤 | 不可评拦下 | 分离度 | 整体准确率 |
|---|---|---|---|---|---|
| ⭐ **保守（推荐）** | −0.1703 | **4.2%**（4/95） | **36.4%**（20/55） | **+32.2pp** | 74.0% |
| 折中 | 0.0575 | 18.9% | 54.5% | +35.6pp | 71.3% |
| 激进 | 0.3922 | 40.0% | 89.1% | +49.1pp | 70.7% |

**现状 = 100% 出标签、0 张拦截。** 保守档在 150 张里多拦下 20 张不该判的，代价是误拦 4 张。

### 8.5 head 与人脸判据的互补（`tool/_scene_face_head_merge.py`）

| 判据 | 可评误伤 | 不可评拦下 | 分离度 |
|---|---|---|---|
| head 单独 | 4.2% (4/95) | 36.4% (20/55) | +32.2pp |
| 人脸单独 | 2.1% (2/95) | 18.2% (10/55) | +16.1pp |
| head ∪ 人脸 | 6.3% (6/95) | 40.0% (22/55) | +33.7pp |
| head ∩ 人脸 | 0.0% (0/95) | 14.5% (8/55) | +14.5pp |

**关键增量**：不可评里「**没脸**」的 29 张 —— **人脸判据 0/29 一张都拦不到**，
而 head 在这 29 张里拦下 **7 张（24.1%）** ⇒ 这是 head 独有的能力。

**⇒ 结论：head 单独就够**。并集只多拦 2 张不可评、多误伤 2 张可评（性价比一般），
人脸判据可作为**可选的第二道保险**（交集档误伤 0%）。

### 8.15 动作 / 情绪标签：**零样本实测不通**（2026-10-15）

**诉求**（用户原话）：「还有很多不同的分词，比如动作、大笑、跑步、开心、哭泣、划船、跳舞、游泳，这些好像都没有分词……

**架构判断：这个方向对，而且与「加词表掉点」不矛盾。**
2.6 测出的「加主体/季节类掉 4~7 个百分点」，前提是**硬并进同一个 408 类词表** ——
融合层用 `zscoreAcrossClasses` + softmax 做**跨类**归一化，多一个类就稀释旧类的票。
而动作/情绪天然是**多标签**（一张照片可以既「海边」又「划船」又「大笑」），
正确做法是**各维度各出各的 Top-K**，搜索侧并集返回 —— 这样不抢票（§3.3 已是这个设计）。
所以问题不是「能不能加」，而是「**CLIP 零样本判得动吗**」。

#### 8.16.3 逐项判断

**① 15 类动作模型（apache-2.0）—— 不能用。**
它是**闭集强分类**：喂静物（礼品盒/桌面/无人小艇）也照样给出 `Sleeping 70%`/`Dancing 20%`，
**没有任何「不知道」出口**。整图 Top-1 **0/15**；换成「人脸框 3× 外扩的人像区域」后
只在**大笑**那张命中（`Laughing 63%`），2/8 之一。原因：15 类太窄、训练集与真实相册分布差太远。

**② 400 类 TimeSformer（cc-by-nc-4.0）—— 定性最像样，但不能发布。**
整图下 **5~6 张语义说得通**：过溪 100%、瑜伽 97%×2、皮划艇 70%、用餐 69%、羽毛球 61%。
这是三者里唯一「看得出在干什么」的。但：
- **许可证是 CC-BY-NC-4.0**（继承自 facebook 原仓），**商用禁止** ⇒ 进不了产品；
- 它是**视频模型**（8 帧输入），单张照片只能把同一帧复制 8 份，属 hack；
- 而且给它喂「人像区域 3×」反而**更差**（丢掉场景上下文）⇒ 说明它靠的其实是场景线索，不是人体动作。

**③ 7 类表情模型（apache-2.0）—— 许可证干净、大笑能对上，但还不敢用。**
必须喂**人脸裁剪**（整图测是不公平的）：
- ✅ 有情绪真值的 3 张里命中 1 张（大笑 → happy 99%）；
- ❌ 微笑 → `neutral 66%`（happy 只排第 2）、另一张微笑 → **`angry 48%`** —— 这个错得离谱；
- ⚠️ **人脸检测本身在漏**：漫展双人、山顶三人合影都没检出脸（远景/小脸被 `isFaceBoxAcceptable` 挡掉）。
- **n=3 太小**，不足以下结论；但「装上就能用」显然不成立。

#### 8.16.4 待办（按优先级）

1. **扩大评测到可信样本量**：表情至少 30~50 张有明确表情的（现在只有 3 张有真值）；动作每类 10 张。
2. **找许可证干净的动作模型**：torchvision 的 Kinetics 权重是 BSD 系（`r2plus1d_18`/`mvit_v2_s`），
   但要装 torch 做 ONNX 导出（CPU 版约 200MB，代理可下）。这是目前最可能的正解。
3. **零成本路线并行推进**：人脸 + 时间 + 场景 组合检索（合影/单人/无人、「某人的某次事件」），
   只用人脸检测就够，不依赖上面任何一个模型。
4. 体积账：动作 87MB + 表情 87MB = **安装包 +174MB**（TimeSformer 再加 123MB）。
   要不要进包，得先看 2、3 的结论。

**顺带发现（对词表设计有用）**：15 张里 **6 张是「拍照摆姿势」** —— 旅行照的主体行为高度集中。
如果真做动作标签，这类**泛化标签会成为新的 hub**，必须显式处理
（要么做成独立的「构图类型」维度：单人摆拍/多人合影/抓拍，要么限制其召回）。

### 8.17 SigLIP 2 开放词汇实测：**这是正解**（2026-10-15）

**结论**：SigLIP 2 在同一套 15 张真值图上，**Top-1 60% / Top-3 86.7%（英文候选）**，
把 CLIP 零样本（0/15）和 15 类闭集模型（0/15）**按在地上**。而且**相近活动能分开 5/5**。

#### 8.17.1 三方对比（同一套 15 张人工真值）

| 方案 | Top-1 | Top-3 | 静物拒识 | 相近活动区分 | 许可 | 单图 |
|---|---|---|---|---|---|---|
| CLIP b32 零样本（47 类动作/情绪） | **0/15** | 2/15 | 0/3 | 无信号 | 已用 | ~130ms |
| 15 类闭集动作模型 | **0/15** | — | 0/3（无拒答） | — | apache-2.0 ✅ | — |
| 400 类 TimeSformer | 定性 5~6/15 | — | — | — | ⛔ cc-by-nc | — |
| ⭐ **SigLIP 2 base-224（英文候选）** | **9/15 = 60.0%** | **13/15 = 86.7%** | **3/3** | **5/5** | **apache-2.0 ✅** | **94ms** |
| SigLIP 2（中文候选） | 6/15 = 40.0% | 15/15 = 100% | 1/3 | — | 同上 | 94ms |

**典型命中**：敬茶 →「端着茶盘敬茶」；爬山过溪 →「hiking through a forest stream」；
山顶瑜伽 →「doing yoga on a mountain」；静物礼盒 →「giftbox」；无人小艇 →「unrelated」。

**相近活动区分（英文分差）**：badminton 0.103 > volleyball 0.087 > tennis 0.076；
hiking 0.130 ≫ cycling 0.027 > swimming 0.019；yoga 0.137 ≫ running 0.064 > cycling 0.034；
laughing 0.076 > smiling 0.065 > singing 0.036；kayaking 0.062 ≫ swimming 0.018。
⇒ **这是 CLIP 和闭集模型都做不到的**。

#### 8.17.2 体积账（这一点决定了它能不能进包）

| 组件 | 体积 | 要不要随包发布 |
|---|---|---|
| `vision_model_q4f16.onnx` | **52 MB** | ✅ 要（运行时唯一的模型） |
| `vision_model_int8.onnx` | 90 MB（**本机跑不了**，见下） | ❌ |
| `text_model_q4f16.onnx` | 422 MB | ❌ 构建期用完就丢（与现有 CLIP 文本塔同理） |
| `tokenizer.json` + `tokenizer.model` | 38 MB | ❌ 构建期 |

⇒ **运行时只增 52MB**，与现有 CLIP 视觉塔（85MB）**同量级** —— 「SigLIP 2 要 1.5GB」是把
fp32 全量当成要分发的东西了；按现有「只发视觉塔 + 构建期预计算文本嵌入」的做法，**代价很小**。

#### 8.17.3 ⚠️ 集成前必须处理的三个硬约束

1. **int8 版在本机 onnxruntime-node 1.20.0 跑不了** —— 报
   `Could not find an implementation for ConvInteger(10)`（QOperator 量化，CPU EP 不支持）。
   **实测 `q4f16` 可用**；如果将来要 int8，得先升 ORT 版本。
   ⚠️ 另：`vision_model_q4f16.onnx` 第一次下载被**截断**（40.8MB vs 应有 54.6MB），
   解析报 `Protobuf parsing failed` ⇒ **下完必须校验字节数**。
2. **SigLIP 属另一个模型族**：sentencepiece 分词器（不是 CLIP 的 BPE）、mean/std 0.5、
   `pooler_output` 才是句向量（`last_hidden_state` 是逐 token 的，拿它算相似度毫无意义）。
   ⇒ **不能复用 `clipTokenizer.js`**，要单独接一条链路（本轮的 `_siglip_text_ids.py` 是最小验证）。
3. **中文能用，但明显弱于英文**：Top-1 60% → 40%，**静物拒识 3/3 → 1/3**。
   ⇒ **不能砍掉现有的「中文查询 → 英文候选」翻译层**；中文只适合做**展示标签**，不适合做匹配串。
   （对比：CLIP 词表 49408 个 token 里 **0 个含 CJK** ⇒ SigLIP 2 已是质变，中文被切成 5~9 个
   按词 token 而非按字节。）

#### 8.17.4 拒识怎么做（对上了 8.15 的教训）

英文候选里放「An unrelated photo that does not match the activities above」这类锚点，
**静物 3/3 都落到锚点或 giftbox 上** ⇒ 英文下「拒识」这件事**天生就能做**。
但同一套锚点在**中文**下只挡住 1/3，且对正常照片**误拒偏多**（15 张里 5 张被 unrelated 抢了 Top-1）。
⇒ 仍建议照 8.4 的老路：**锚点只做特征，最终阈值用一个小 head 或分位数标定**，
不要指望「加一个 unrelated 候选」就自动获得拒识能力。

#### 8.17.5 待办

1. **扩评测**：15 张太少。按 8.17.3 的口径扩到每类 ≥10 张，重点是「相近活动易混对」。
2. 决定 SigLIP 2 的位置：是**替换** CLIP 视觉塔，还是**并存**（场景走 CLIP+Places365 的 408 类，
   活动走 SigLIP 2 的开放词表）。并存要给安装包 +52MB 和一份额外的推理耗时。
3. `SmolVLM-256M-Instruct`（apache-2.0，已验证）留作二线：需要**自然语言描述**时再上，
   它是自回归生成，逐图成本与图文匹配不是一个量级，**不建议**用来给整库打标签。

### 8.18 扩评 + 上大模型：**结论是「别上」**（2026-10-15）

用户放开了体积预算（「1G 左右都可以，最主要还是识别效果」）并要求**许可必须可商用** ⇒
TimeSformer（cc-by-nc）出局，SigLIP 2 全系（apache-2.0）可挑。于是把评测集从 15 张扩到 **26 张**、
候选从 20 个扩到 **25 个**（补了乒乓球/跳舞/拥抱/篮球/足球），并把旗舰也拉进来对比。

#### 8.18.1 对比集构成（26 张，全部人工看图定真值）

按**已有场景标签分层抽样**（室内外游泳池/宴会厅/美食广场/演出场馆/舞厅/健身房/运动场/球类场），
再补 3 张静物与截图作为**拒识负样本**（共 5 张「无动作」）。
真值分布：拍照摆姿势 ×7、游泳 ×3、合影/聚餐 ×2、敬茶/微笑/大笑/爬山/吃饭/乒乓球/跳舞 各 1、**无动作 ×5**。

#### 8.18.2 三个模型并排（同一套 26 张 / 25 候选）

| 模型 | 语言 | Top-1 | Top-3 | 仅活动 Top-1 | 静物拒识 | 相近活动 | 单图 CPU | 视觉塔 |
|---|---|---|---|---|---|---|---|---|
| **base-patch16-224 q4f16** | 英 | **16/26=61.5%** | 23/26=88.5% | 15/26 | 5/5 | 5/5 | **98 ms** | **52 MB** |
| base-patch16-224 q4f16 | 中 | 13/26=50% | 22/26 | 14/26 | 2/5 | 4/5 | 98 ms | 52 MB |
| so400m-patch14-384 fp16 | 英 | 16/26 | **24/26=92.3%** | **17/26** | 5/5 | 5/5 | **2075 ms** | 817 MB |
| so400m-patch14-384 fp16 | 中 | **17/26=65.4%** | 25/26=96% | 17/26 | 2/5 | 5/5 | 2075 ms | 817 MB |
| so400m-patch14-384 q4f16 | 英 | 15/26 | 24/26 | 15/26 | 5/5 | 5/5 | 1849 ms | 235 MB |
| so400m-patch14-384 q4f16 | 中 | 16/26 | **26/26=100%** | 16/26 | 2/5 | 5/5 | 1849 ms | 235 MB |

**① 大模型几乎没有收益，却慢 21 倍。** 英文 Top-1 **持平（16/26）**，Top-3 只 +1，
仅活动 Top-1 +2。代价是 **98ms → 2075ms（21×）**：6 万张照片从 ~1.6 小时变成 **~34.6 小时**。
且 817MB fp16 与 235MB q4f16 **几乎没差** ⇒ 就算要上也不该选 fp16。

**② 三个模型在绝大多数错误上是「一起错」的**（#2/3/5/7/11/12/16/21/23 全错），
只有 #17/#26 这种零星差异 ⇒ **瓶颈不在模型容量**。

**③ 唯一明显受益的是中文**：Top-1 50%→65.4%、相近活动 4/5→5/5。
但既然中文只当展示标签、匹配仍走英文（8.17.3），这点收益换不来 21 倍耗时。

**⇒ 结论：停在 base-patch16-224（52MB / 98ms），不要上 so400m。**

#### 8.18.3 ⭐ 真正的瓶颈找到了：拒识锚点是「hub」

`unrelated` 这条候选在 base224 英文下**抢走 26 张里的 11 张 Top-1，其中 7 张是判错的**
（本该是活动/摆拍的照片被它吞了）。而泛化候选（posing/hugging/groupphoto/laughing/smiling）
只抢 4 张、错 1 张 —— **问题远没有想象中大，最大 hub 就是拒识锚点本身**。

这正好印证 8.15 / 8.17.4 反复说的「锚点参与同一轮 max 竞争天然有偏」。

#### 8.18.4 ⭐⭐ 改「事后阈值」后，分离度是完美的

把拒识从「多一个候选参选」改成「**先只在活动候选里排序，再用阈值判这张到底有没有活动**」：

| 模型 | 有活动的 21 张（仅活动 Top-1 分数） | 无动作的 5 张 | 阈值 | 结果 |
|---|---|---|---|---|
| **base224** | min **0.078** / 中位 0.111 | max **0.067** / 中位 0.058 | **0.068** | **无动作 5/5 拦下，有活动 0/21 误伤** |
| so400m384 | min 0.051 / 中位 0.092 | max 0.055 / 中位 0.035 | 0.056 | 5/5 拦下，误伤 1/21 |

**两组分数完全不重叠**（0.067 < 0.078）——比锚点做法的「抢 11 次错 7 次」好到不是一个量级。
而且 **base224 的分离度比 so400m 还干净**，又一次说明不用上大模型。

⚠️ 但阈值 0.068 是**从这 5 张负样本标出来的**，n 太小、有过拟合风险；
要照 8.4 的老路用**分位数/小 head** 正式标定，并扩负样本到 ≥30 张再定稿。

#### 8.18.5 待办（按性价比）

1. **拒识改事后阈值**（最高性价比）：先活动排序取 Top-1 → 分数过阈值才给标签 → 不过就归「无活动」。
2. **扩负样本**：现在只有 5 张「无动作」，阈值标不准。
3. **与现有场景标签融合**：库里每张照片已有 408 类场景标签，可做事后融合
   （例：场景=室内游泳池 ⇒ 抬 `swimming`；场景=演出舞台 ⇒ 抬 `dancing`）。零新增模型，预期收益比换大模型高。
4. 修 `posing` 这类泛化候选的召回（目前不是主要矛盾，排后面）。
5. ❌ **不要再换更大的模型** —— 8.18.2 已经证明没收益；除非上面 1~3 做完仍是瓶颈。

### 8.19 扩负样本 + 拒识阈值定稿：**修正 8.18.4 的「完美分离」**（2026-10-15）

#### 8.19.1 ⚠️ 先修正上一轮的错误结论

8.18.4 说「改成事后阈值后两组分数**完全不重叠**（负类 max 0.067 < 正类 min 0.078）」——
**那是只有 5 张负样本造成的假象**。把负样本扩到 32 张后，重叠是 **0.030**（正 min 0.078 vs 负 max 0.108）。
**教训：阈值类结论必须看负样本量，n=5 时「完美分离」没有意义。**

#### 8.19.2 负样本怎么扩的（这套方法可复用）

1. **不能用场景标签抽「无人照」** —— 实测按 `海滩`/`服装店` 抽 30 张，**19 张有人**（人像/活动照）。
2. 改用 **人脸检测预筛**（`tool/_pick_negatives.js`）：候选池 400 张，留 0 脸的。
3. **拼 contact sheet 一次看完**（`tool/_mk_contact_sheet.js`，30 张拼成 1 张图）⇒ 人工逐格确认。
   用这个方法还顺手发现：**人脸检测会漏检明显的人像**（小孩特写、戴口罩自拍、眼镜正脸都检成 0 脸）。
4. **必须回头清标签**：负样本按分数排序看 Top-18，发现 **9 张其实含人**（摆拍/自拍/远处小人/剪影）。
   既然候选里有 `posing`/`smiling`，**含人照片不该算负样本** ⇒ 剔除。

最终评测集：**53 张（正 21 / 负 32）**，负样本 = 纯风景 / 静物商品 / 截图文档，全部**无人**。

#### 8.19.3 拒识：事后阈值 + k 折交叉验证（τ 在训练折选、测试折评）

| 模型 | 语言 | AUC | τ 中位 | **测试折拦下** | 测试折误伤 | 重叠 |
|---|---|---|---|---|---|---|
| **base-patch16-224** | 英 | **0.955** | 0.078 | **78.8%** | 6.2% | 0.030 |
| base-patch16-224 | 中 | 0.814 | 0.077 | 44.5% | 5.5% | 0.044 |
| so400m-patch14-384 | 英 | 0.930 | 0.051 | 76.4% | 5.5% | 0.045 |
| so400m-patch14-384 | 中 | 0.863 | 0.078 | 53.9% | 5.2% | 0.057 |

**⇒ 事后阈值这条路成立**：英文下 AUC **0.955**，5% 误伤能拦下 **78.8%** 的无活动照片。
（对照：把拒识候选放进排序里「参选」的做法见 8.18.3 —— 它会变成 hub，抢 11/26 错 7。）

#### 8.19.4 顺带复验：大模型在难负样本上**仍然没有优势**

| 模型 | 英文 Top-1 | 英文 Top-3 | 拒识 AUC | 单图 |

+1 张 Top-1、+2 张 Top-3，换 **20 倍耗时**，而且**拒识 AUC 还更低**。
⇒ 8.18.2 的结论在更难的负样本上**依然成立，可以彻底定案：用 base-patch16-224。**

#### 8.19.5 中文仍然明显偏弱（拒识也必须走英文）

中文 AUC 0.814 vs 英文 0.955；拦下率 44.5% vs 78.8%；Top-1 50.9% vs 71.7%。
⇒ **拒识阈值也要用英文候选算**，中文只做展示标签（与 8.17.3 一致）。

#### 8.19.6 场景标签融合：可行但只能「白名单」

把库里已有的 408 类场景标签拉出来对照（21 张正样本全部查到）：

- ✅ **强对应、直接可用**：`天然泳池`/`游泳馆` → 游泳（3/3 全对）；`美食广场` → 吃饭/聚餐（2/2）；`舞厅` → 跳舞；`木筏` → 爬山。

#### 8.19.7 待办

1. **把拒识定稿成产品逻辑**：活动候选排序 → Top-1 分数过 τ 才给标签 → 否则「无活动」；τ≈0.078（英文）。
2. **白名单场景融合**（零成本，先做）。
3. 负样本再扩到 ≥100 张把 τ 压稳（现在 32 张，τ 的置信区间还宽）。
4. ❌ 不要换模型；❌ 不要把拒识候选放进排序里参选。

### 8.20 负样本扩到 196 + 找到拒识的**根因**（2026-10-15）

用户：「主要识别国内常见的场景，什么冰球馆这些国内少的，不用管。」

#### 8.20.1 先纠正一个直觉：**高频 ≠ 常见**

按全库 64136 张统计类频次，Top-30 里赫然是 `沙漠`(1623)、`室内溜冰场`(1511)、`游戏厅`(949)、
`木筏`(759)、`更衣室`(725)、`消防站`(709)、`淋浴间`(678)、`议事厅`(642)、`白板`(669)——
**一个中国用户的相册不可能有 1600 张沙漠**。这些高频类是模型在中文照片上**乱输出了 Places365 的西方类**。
⇒ **不能拿类频次当「国内常见度」用**。长尾：≤5 张的有 46 个类（共 127 张，0.20%）。

#### 8.20.2 负样本从 32 扩到 196（方法上踩了两个坑）

| 做法 | 结果 |
|---|---|
| ❌ 按场景标签随机抽「无人照」 | 抽 30 张，**26 张其实有人**（远处小人/侧脸/背影/戴口罩，人脸检测全漏） |
| ✅ 改**定向抽「本来就没人」的类**（文档截图 / 静物食物 / 纯风景 / 宠物） | AUC 0.894 → **0.928** |
| ✅ 再**只核高分端前 60 张**（阈值由高分端决定） | top-60 里 **36 张其实有人**（婴儿喂饭、海边人群、挑担子）⇒ 清掉后 AUC → **0.966** |

⚠️ **人脸检测在 0 脸候选里仍放进来大量人像**（婴儿特写、戴口罩自拍、眼镜正脸）——
**不能只靠它当「无人」的筛子**，最终必须有看图环节。

评测集最终 **217 张（正 21 / 负 196）**。

#### 8.20.3 拒识定稿（k 折 CV，τ 训练折选、测试折评）

| 模型 | 语言 | AUC | τ 中位 | **测试折拦下** | 测试折误伤 |
|---|---|---|---|---|---|
| **base-patch16-224** | 英 | **0.966** | 0.078 | **87.4%** | 5.5% |
| base-patch16-224 | 中 | 0.817 | 0.077 | 38.3% | 5.0% |

⇒ **英文下这套可以用**：5.5% 误伤换 87.4% 的无活动照片被挡住。**中文依然必须走英文候选。**

#### 8.20.4 ⭐ 找到拒识的根因：图文模型匹配「物体」，不匹配「动作」

清完标签噪声后，仍**有 26 张真·无人的负样本分数超过正类最小值**。逐张看图后发现，
它们都是**含「活动关联物体」的照片**：

- 湖中小船 → 匹配 `kayaking`（**照片里根本没人**）
- 桌面棋盘 → 匹配 `playing cards`
- 书本 / 白板 / 图纸 → 匹配一堆活动
- 日落海滩 → 匹配 `posing` 之类

**这不是标签错，也不是阈值没调好，是编码器的结构性局限**：SigLIP 学的是图文语义相似度，
它分不清「**照片里有船**」和「**有人在划船**」。这也解释了为什么 8.18 里 400 类 TimeSformer
喂「人像区域」反而更差 —— 它靠的同样是场景/物体线索。

#### 8.20.5 解法方向验证：加「照片里有没有人」的门

想法对，但**用文本提示实现无效**：

| 实现方式 | margin AUC | 门控单独（拦/留） | 门控+阈值（拦/留） |
|---|---|---|---|
| `There is a person` vs `There is no person` 文本对 | **0.627** | 拦 47% / 留 52% | 拦 96% / **留 52%** |
| （对照）只用阈值 | — | — | 拦 87.4% / **留 94.5%** |

**margin AUC 只有 0.627** —— SigLIP 对「否定式提示词对」几乎无判别力（这与它训练时用的是
「图文是否匹配」而非「两个描述哪个对」有关）。门控+阈值虽然把拦下率提到 96%，
但**丢掉一半的正样本**（留 52%），得不偿失。

⇒ **结论：需要真正的人物检测器**（不是文本提示、也不是人脸检测——人脸检测漏检太严重）。
候选：SSD-MobileNet（Apache-2.0）/ RT-DETR（Apache-2.0）/ YOLO 系（⚠️ AGPL，需谨慎）。
这是本轮得出的**明确下一步需求**。

### 8.22 拒识标签口径修正 + q4f16 定稿 + 活动维度集成方案（2026-10-15）

#### 8.22.1 ⛔ 先拆掉一个陷阱：不能用门控改标签再拿门控评估

按 8.21.5 的待办 2「收紧口径：人检出为 0 才算无活动」，
第一版直接把 `personProb >= 0.5` 的照片改标为「有人」，重跑评估——
结果 **负样本 AUC 1.000 / 拦下 100.0%**。

**这是循环论证**：负样本集合被定义成「DETR 说没人」，再用 DETR 的门线去判，必然全对。
**⇒ 任何「用模型输出改真值、再用同一模型评估」的做法都会得到假的天花板。**
本条纪律写死：**改标签只能依据人工看图。**

#### 8.22.2 真正的问题比 8.21.3 说的严重得多

8.21.3 只报了「门控+阈值仍挡不住的 19 张」。把范围放宽到**所有** `personProb ≥ 0.999`
的「无活动」照片，数量是 **71 张 / 196 = 36.2%**（不是 19 张）。

负样本的人目概率分布（q4f16）：

| 区间 | 张数 | 占比 |
|---|---|---|
| [0.00, 0.05) | 2 | 1.0% |
| [0.05, 0.20) | 9 | 4.6% |
| [0.20, 0.50) | 33 | 16.8% |
| [0.50, 0.90) | 51 | 26.0% |
| [0.90, 0.999) | 34 | 17.3% |
| **≥0.999** | **67~71** | **34~36%** |

**中位数 0.928** ⇒ 所谓「无活动」的 196 张里，绝大多数 DETR 都看到了人。

#### 8.22.3 人工复核（4 张拼图，71 格逐格看）

工具：`_mk_contact_sheet.js` 拼图 → 我逐格判 → 落到
`tool/_tmp/_regrade_manual.json`。**只依据肉眼，不看分数。**

结果（71 张）：
- **57 张其实是人物照**（人像/合影/有人做事/有人在画面里）⇒ 从负样本剔除；
- **14 张确实无人**，但 DETR 误检为有人 ⇒ **保持负样本**，这就是门控的假阳性：
  - **手机截图**类（微信对话、二维码、外卖/银行/健康 App 界面）
  - **静物**类（餐具里的汤、榴莲披萨、椰子甜品）
  - **手持物**类（手持拖鞋商品、手持温度计、手持打印发票）
  - **纸张文件**类（手写笔记、体检报告、打印处方）
  - **纯风景**类（无人机航拍、山景）

⚠️ 这里定了一条**产品口径**（写进文档，不要来回改）：

> **「无活动」= 照片里没有从事活动的人。**
> 手部出镜、容器餐具、桌面棋盘、纸张文件、手机截图、纯风景、静态商品

**关键设计约束（都踩过坑）**
1. **场景与活动不共享标签空间**：活动标签写入**独立列**（`act_name`），
   不并进 `place_name` —— 否则 408 类的 z-score 校正与权重排序全被污染。
2. **门控在阈值之后跑**：先把不确定带筛出来（9.4%），再跑 DETR，避免全库 60k×373ms。
3. **中文只做展示**：活动候选的匹配一律走英文提示词，中文标签是 `act_candidates.json`
   里的 `zh` 字段（8.17 已证中文 Top-1 从 60% 掉到 40%）。
4. **`hasperson` / `noperson` 必须移出排序**（8.20.6 的坑），它们只是门控用。
5. **不改 `photo_places` 计数语义**：活动相册走自己的聚合，`weight_sum` 不动。

**入库形态：独立成表，不挂在场景表上**（⚠️ 与原计划不同，是实施时改的）

原计划是给 `photo_places2filehash` 加 `act_name/act_score/act_alt` 三个列。实施时否掉了：

> **被可判性 head 拦下的照片（约 10.8%）根本不写 `photo_places2filehash` 行**（§8.7/§8.10：拦下 = 不写行）。
> 而人像 / 合影 / 婚礼这类照片**恰恰是「合影/摆拍/大笑」最该命中的对象**
> （§8.14 实测：以人为主体的婚礼现场 28%、演出场馆 24%、服装店 45% 会被拦下）。
> 挂在场景行上 ⇒ **这些照片连活动标签一起丢**，正好丢掉最需要的那一类。

所以活动维度用两张**独立表**（与场景两张表对称）：

| 表 | 关键列 | 说明 |
|---|---|---|
| `photo_activity` | `act_key`(PK) / `act_name` / `photo_count` / `score_sum` / `count_high` / `is_hide` | 聚合（对标 `photo_places`） |
| `photo_activity2filehash` | `act_key` / `act_name` / `act_score` / `act_status` / `act_alt` / `file_hash`(UNIQUE) | 明细（对标 `photo_places2filehash`） |

**行数语义**：**只在「有活动」时写行**。实测 97.1% 照片被判无活动，若也写行会把表撑大 30 倍。
「跑过但无活动」与「还没跑」的区别由 `photo_index.gen_activity` 承载。

**主键用英文 `act_key`**（swimming / dining…）而不是中文展示名：程序判断用 key、中文只做展示，
避免以后改文案把数据打散。

#### 8.23.2 ⭐ 集成时抓到的两个真 bug（都会静默错数据，必须记住）

**bug 1：personProb 没归一化 ⇒ 正样本被大量误杀**

`tool/_person_gate_probe.js` 落盘时做了 `+best.toFixed(4)`，DETR 在有人图上 sigmoid 饱和到
`0.9999x` ⇒ 被归一化成 `1.0`。而生产模块第一版返回**原始值** `0.99998787`。
τp = 1.0，于是 `p < 1.0` 成立 ⇒ **被判成「没人」**。

实测后果：**保留率 93.6% → 71.4%（6/21 正样本假阴）**。
修法：生产模块也做 `toFixed(4)`，并写死注释「必须与标定口径逐字一致」。

**bug 2：`onConflict().ignore()` 在 better-sqlite3 下返回 `[undefined]` ⇒ 聚合计数虚高**

`Array.isArray(x) && x.length > 0` 会把「被忽略的插入」判成「插入成功」。
实测：同一 `file_hash` 提交 4 次，明细表 3 行（正确）但 `photo_count = 3`（应为 2）。

修法：**写库前先按 `file_hash` 预检查**（场景维度一直是这么规避的，活动维度照做）。
`tool/_activity_db_test.js` 有 14 项断言把守这两点。
