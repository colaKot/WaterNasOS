## 一、每日一帧点开后不能翻页

**根因**：`_DayFrameTile` 点开走的是 `openSinglePhoto(fullpath, title)` —— 查看器的列表只有**这一张**，
左右按钮、键盘左右都只是“在一张里翻”，自然没反应。

**改法**（`recall/view/photo_day_frame_view.dart`）：
- 新增 `_openDayFrames(ctrl, index)`：把**整组帧**按 `fullpath` 打包成列表交给 `openPhotoImages`，
  索引按「过滤掉空路径后的位置」计算，中间有坏数据也不会打开错的那张；
- 单帧点击改为 `onTap: () => _openDayFrames(ctrl, i)`；
- 键盘能力本来就在 `CustomGalleryController._handleKeyEvent` 里（← → 翻页、ESC 关闭、Del 删除、
  Ctrl+I 信息、空格播实况），列表给对了就全部可用，无需另写。

**箭头交互**（`gallery/views/components/gallery_navigation_arrow.dart` 重写）：
- 变为 `StatefulWidget`：鼠标移入 ⇒ 圆形底 0.42→0.62、描边提亮、`AnimatedScale` 放大到 1.10、
  箭头朝行进方向轻推 2px；
- 按下 ⇒ 缩到 0.92（120ms easeOut），松开回弹；
- 首张的左箭头 / 末张的右箭头 ⇒ 0.38 透明度禁用态 + `cursor: basic`，不再“点了没反应像卡住”；
- 总张数 ≤ 1 时两个箭头都不显示。

## 二、相册子页面的关闭层级

**根因**：桌面相册窗口右上角 X 直接走 `PcHomeController.closeApp('photo')` ⇒ `windows.closeWindow`，
不区分当前在看哪一页。从首页点进「我的足迹 / 相册 / AI / 回忆」后一按 X，整个相册就没了。

**改法**：
- `PhotoHomeController` 新增 `isRootPage()` / `isRootPageNow` / `backToTimeline()` / `interceptWindowClose()`；
  根层级只有两个：`home`（首页）与 `all.timeline`（时间轴）。
- `PcHomeController.closeApp()` 开头拦截：`app == 'photo'` 且当前不是根层级 ⇒ 切回 `all.timeline` 并返回，
  **不关窗**；只有首页/时间轴按 X 才是真的关相册。
- 侧栏顶部（`photo_left_menu.dart` 的 `headerTrailing`）在子页面时显示「← 时间轴」，点一下同样回时间轴；
  根页面仍显示照片总数。

→ 效果：子页面按 X = 退一层；再按一次（已在时间轴）= 关窗口。

## 三、搜索结果「一天一个标题、底下一两张」

**根因**：搜索结果按**相似度（rank）**排序，而列表渲染按 `originalDate` 变化插日期头
（`TimelineListDateHeader`）。rank 序里日期是交错的 ⇒ 几乎每张照片都触发一个新日期头，
于是每条只有 1~2 张、行数极长。

**改法**（`timeline/controller/parts/photo_timeline_pagination.dart`）：
1. **按日期聚拢**（`_clusterSearchByDate`）：搜索结果先按 `originalDate` 分桶，同一天的连续排列；
   组间顺序沿用「该日期第一次出现的位置」⇒ 相关性最高的那天仍排最前，组内保持相似度顺序。
2. **稀疏日期不再单独占一个头**（`_searchSparseDates`）：某天 ≤2 张时不插日期头，照片直接接在前一段继续排，
   把空出来的行填满；如果整批全是稀疏日期，只保留第一个日期做锚点（滚动定位需要）。
3. **跨页归并**（`_mergeSearchPhotos`）：翻页时若该日期已在列表里，就插回那一天的组尾，
   而不是在末尾再起一个重复日期头；稀疏日期在翻页时同样不新开头。

非搜索状态完全走原逻辑（时间轴本身就是时间序，不需要聚拢）。

⚠️ 分页仍按 `boundaryPhoto.originalDate` 取时间窗。聚拢保持「组首次出现顺序」，
所以批内首尾日期不变，时间窗不会错位。

## 四、gexuan 账号人脸混淆（父子 / 表兄弟）

用户反馈：本人与儿子容易混，儿子（街街）与表哥容易混；已手动把问题严重的脸标成「有问题」，
但效果有限。

### 4.1 之前为什么「标了有问题也没用」

`photo_faces.is_hide=1` 只影响**列表展示**（`faceService.listFaces` 过滤），
`faceWorker` 的原型匹配与二次合并**完全不看这个字段** ⇒ 被标记的组照旧继续吸脸，越吸越大。

### 4.2 本轮四条护栏（`workers/ai/faces/faceWorker.js`）

| # | 规则 | 说明 |
|---|---|---|
| 1 | **已命名组认领加严** | 命中组有名字（用户确认过身份）⇒ 门槛 `req + ai_face_named_extra_req`（默认 0.05）、裕度再 +0.02。父子/兄弟相似度天然偏高，只对“确认过的组”加严，不必牺牲全库召回 |
| 2 | **两个已命名组禁止二次合并** | 「街街」并进表哥就是这一步干的。只有 `sim` 与 `simBest` 都 ≥ `FACE_NAMED_PAIR_MERGE_SIM`（默认 0.72）才放行 |
| 3 | **同图共存 ⇒ 禁止合并** | 两组如果曾出现在同一张照片里，铁定是两个人。合并前用 `(file_hash, face_id)` 唯一索引做一次 join，命中就跳过。这是最硬的证据 |
| 4 | **「有问题」组退出聚类** | `is_hide=1` 的根人脸不参与认领、不参与合并（本轮新增 `hiddenRootIds`，启动加载 + 每轮维护刷新）。标完之后它不再吸人，新脸会新建组 |

另外两条配套：
- 默认认领裕度 `ASSIGN_MARGIN` 0.04 → **0.06**（文档 6.3 的建议值本来就是 0.08）；
- **灰区不更新原型**：相似度只比门槛高 `PROTO_GRAY_ZONE`（0.02）以内时不更新原型
  （映射照常写入）。避免一次误认领把整组原型往错方向带，后面越认越像。

### 4.3 可调参数

| 键 | 默认 | 范围 | 含义 |
|---|---|---|---|
| `ai_face_sim_thresh` | 0.45 | 0.2~0.9 | 全局认领相似度 |
| `ai_face_assign_margin` | **0.06** | 0~0.3 | 与第二名的裕度 |
| `ai_face_named_extra_req` | **0.05** | 0~0.2 | **已命名组的额外门槛（本轮新增，父子场景优先调它）** |
| `ai_face_named_extra_margin` | 0.02 | 0~0.2 | 已命名组的额外裕度（环境变量） |
| `ai_face_second_merge_thresh` | 0.45 | 0.2~0.9 | 二次合并阈值 |
| `FACE_NAMED_PAIR_MERGE_SIM` | 0.72 | 0.3~1 | 两个命名组仍允许合并的相似度（环境变量） |

接口：`POST /api/photo/face/tuning/set`（超管），body 可带 `namedExtraReq`；
`POST /api/photo/face/tuning/get` 回读。

### 4.4 重跑步骤（不丢名字，推荐）

1. 热更 + **重启服务端**（`faceWorker` 是 fork 的子进程，asar 热更换不掉运行中的 worker）；
2. 启动日志确认两行：
   - `[faceCluster] 已命名组 N 个（认领门槛 +0.05），有问题组 M 个（退出认领/合并）`
   - `[FaceTuning] ... namedExtraReq=0.05 namedExtraMargin=0.02`
3. 人脸页打开混得最严重的组（「我」「街街」）→ 多选不属于他的照片 → **移出人脸相册**；
   移出现在是「**移出即重识别**」（见 4.7）：该照片上所有人脸的映射与样本一起清掉、
   `gen_faces` 置 0、并主动拉起 faceWorker 重新识别 —— 重跑时新护栏已生效，错的脸不会再回到原组；
4. 若儿子的碎片组还没名字，先给它命名 —— 命名后立刻按「已命名」加严，后续不会再被表哥吸走；
5. 「有问题」标记保留即可：本轮开始它真正参与聚类（不吸脸、不合并）。

### 4.5 全量重跑（会丢名字）

`POST /api/photo/face/reset`（admin）清空 `photo_faces` / `photo_face_samples` /
`photo_face2filehash` 并把 `gen_faces` 置 0，然后重新识别。
**已命名的人物名会一起丢**，只在“参数已调好、错组遍布全库”时才用。

### 4.6 预期与代价
- 方向明确：**宁可裂开，不要混**。裂开可以「合并人脸」一键修；混了只能逐张移出。
- 代价：同一人物可能暂时裂成 2~3 组（尤其儿童跨年龄），后续维护轮次会按
  「互为最近邻 + 一轮一对一」逐轮收敛。
- ⚠️ 本轮护栏只过了 `node --check` 与逻辑走查，**没有在 gexuan 真实库上做「改前 vs 改后」的混组数量对比**。
  真实效果要看重跑后：命名组的成员纯度、组数变化、日志里 `二次合并跳过` 的条数。

### 4.7 移出人脸相册之后会发生什么（本轮新行为）

**旧行为（有坑）**：`removePhotoFromFace` 只删 `photo_face2filehash` 里那一行，`gen_faces` 仍是 1
⇒ 这张脸从人物里消失，但**永远不会再被处理**；客户端也没接 `/face/rescan-missing`，
想让它重新归位只能全库 `/face/rescan`（清掉可见范围所有映射重跑）。

**新行为**：
1. 删掉该 `file_hash` 上**所有人脸**的映射与样本 —— 必须删干净，因为 `faceWorker.prepareInfer`
   只要看到该 file_hash 还有任意一行就直接跳过；
2. 该照片 `gen_faces=0` 重新入队；
3. 控制器主动拉一次 faceWorker（已在跑 / AI 已暂停 / 开关关闭时不动）。

⇒ **移出 = 这张图重新检测 + 重新认领**。重跑时新护栏已生效，错的脸大概率不会再回到原组，
而是新建组或进正确的人。

两个要知道的副作用：
- 合影里其他人脸的映射会一起重算（通常能回到原组，但那一刻会短暂从人物里消失再回来）；
- 如果这张脸确实与目标组相似度极高，仍可能回到原组 —— 那是模型层面分不开，需要调
  `ai_face_named_extra_req`（0.08~0.10），或用「移动到…」手动指定。

### 4.8 已合并 / 已命名之后还会不会自动学习

会，三个层次同时在学：

| 时机 | 动作 |
|---|---|
| 每张新照片认领成功 | `assignToFace` 按质量加权把新向量混进组原型（alpha 0.02~0.35；**灰区不更新**）。命名与否不影响学习，只影响门槛 |
| 每张新照片 | 写入 `photo_face_samples`（每组保留质量最高的 30 个样本） |
| 每 200 张或 10 分钟 | 用该组 top-25 高质量样本**重建原型**（`rebuildPrototypesFromSamples`）+ 剪枝样本 + 二次合并 |

合并后的组：`mergeFaceInto` 把被并方的原型按 `face_count` 加权混进目标组，之后目标组作为唯一根继续学习；
被并方只剩 `belong_face_id` 这条并查集边，不再参与匹配。

⚠️ 合并是**单向**的（并查集只指向一个根），Flutter 端没有「拆组」按钮，拆开只能靠逐张「移出」。
所以合并前最好确认两人确实同一人；不过本轮的「双命名禁并 + 同图共存禁并」已经能挡掉大部分误合并。
