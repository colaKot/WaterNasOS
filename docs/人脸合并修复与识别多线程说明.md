## 一、这次改了什么（对应铁柱 2026-10-13 的四条反馈）

### 1. 人脸合并失败 / 没反应（`faceService.js` + `ai_faces_controller.dart`）

**根因（代码走查 + 真实库复现）**：合并事务里所有关键 `UPDATE` 都挂着
`.catch(() => {})`，任何一步静默失败事务照样提交 ⇒ 客户端收到 success 但数据
半新半旧，表现就是「合并失败 / 合了但没反应 / 名字丢了」。真实库上纯 SQL
层（INSERT OR IGNORE + DELETE + UPDATE）验证过是好的，栽在错误吞噬上。

**已修**：
- 关键 UPDATE 不再吞错，出错抛穿事务回滚，客户端拿真实错误码
  （新键 `face.MERGE_FAILED`，已在 `api_error_localizer.dart` 注册）；
- **样本跟着合并**：以前 `photo_face_samples` 不迁移，被合并掉的人脸样本变成
  「僵尸样本」（真实库里 1330 条），维护任务按样本会把合并掉的人脸重新养回来；
  现在用 `NOT EXISTS` 防重插入后整体搬迁；
- `proto_best_*` 取两者较优者，不再丢旧方的最佳样本信息；
- `listFaces` / 合并链路统一把 `belong_face_id = 0` 也当根人脸（历史数据写法）；
- 命名接口同样不再吞错（以前写失败也返回 success，用户以为命名成功）。

**进度反馈 + 可取消**（客户端）：
- 合并期间弹进度窗（转圈 + 「正在合并 N 个人物…」），带「取消」按钮 ——
  取消只退出选择态，服务端合并继续跑完，刷新即见结果；
- 合并接口超时 10s → **120s**（大人物组是单事务搬几千行，10s 必挂，
  挂掉还被当成「合并失败」，实际服务端已经合完了）；
- 失败时**保留选择状态**，可直接重试，不用重新勾选。

### 2. 人脸识别多线程（`faceWorker.js`，默认 3 线程可配）

实测（本机，DML GPU，12 张真实照片热身）：

| 配置 | 每张耗时 |
|---|---|
| 1 线程（原状） | 350ms |
| **3 线程（新默认）** | **221ms** |

纯 CPU 机器提升更接近线性。检测（960px E2E）是绝对瓶颈（~300ms/张），
特征提取只要 6ms。识别 53,335 张待处理照片：单线程约 4.4 小时 → 3 线程约 2.8 小时。

**架构**：coordinator 进程内起 N 个 `worker_threads`（同一文件 role=infer），
只做「检测 + 特征提取」；**聚类和 DB 写入仍严格单线程顺序执行**（原型 Map
不能并发改）。批次内两阶段：先并行推理，再顺序入库。

**注意**：线程必须**一个一个起、等 ready 再起下一个** —— 实测 3 个线程
并发初始化 ONNX 会话会把整个进程打挂（rc=127 无输出），串行启动没问题。

**配置**：AI 设置页 → 人脸聚类参数区 → 「识别线程数」下拉（1/2/3/4/6/8，
默认 3）。存 `ai_face_threads`（tableConfig），改后**自动重启识别进程**生效。
也可用环境变量 `FACE_THREADS` 覆盖（优先）。

**人脸大小答案**：每个人脸 512 维 float32 = **2KB**（`feature` 列）；
每个人脸组另存最多 30 个高质量样本（`photo_face_samples`）。

### 3. 智能相册支持人脸条件（`photoSmartAlbumFilterUtil.js` + 相册编辑页）

- 条件字段新增「人脸」：点按钮弹人物列表（头像 + 名字 + 照片数），
  选中后条件值为**人名**（优先）或 `#face_id`（未命名人物）；
- 服务端转成 `whereExists` 关联 `photo_face2filehash + photo_faces`（根人脸）；
- **按人名匹配天然「跟随合并」**：合并人脸时 f2 行整体搬到目标根人脸，
  以后新识别/合并到该人物的照片自动进相册（条件相册是实时查询，无需重建）；
- 未命名人物按 id 匹配，合并后相册会指向新人脸组的旧 id（届时重新选一次即可）；
- 与其他条件（文件名/相机/大小…）可 and/or 组合。

### 4. 场景识别（`placesUtil.js` / `placesWorker.js` / `placesService.js`）

**重置按钮**：入口一直都有 —— AI 场景页右上角「清空」图标（管理员可见），
链路完整（清 `photo_places*` + `gen_place=0` + 重启 worker）。但它是
**纯图标 + hover tooltip**，且藏在场景列表页而非设置页，很难被发现。

本次补做：AI 设置页 → 场景识别开关右侧也放一个文字「重置」按钮
（`_SwitchItem` 新增可选 `onReset` 参数，null 时不显示，人脸/相似项不受影响），
与「重新聚类」「清理误检人脸」并列。走的还是同一个
`POST /api/photo/place/reset`（`requireAdmin`）。
复用已有文案 `reset` / `scene_reset_confirm`，**无需新增多语言 key**。

**模型准确率（如实说明）**：
- 你的库里「病房」是**第一大场景标签（1224 张）**，而「卧室」只有 27 张 ——
  ResNet50-Places365 对室内场景（病房/卧室/育婴室）混淆是出了名的，
  且这些预测置信度很高（0.6~0.88），不是阈值问题；
- 更大的模型只有 Places365 ResNet152（top-1 仅 +2% 左右），**可达的镜像
  （hf-mirror / GitHub / ModelScope）上没有现成 ONNX**；TTA 多裁剪实测
  对这类混淆基本中性（只在低置信样本间重排），故未采用；
- **已加大模型自动探测**：`places365/` 目录下存在 `resnet152_places365.onnx`
  就自动换（预处理与 ResNet50 完全一致，不用改参数），否则回退 resnet50。
  以后拿到更大模型直接丢文件即可，日志会打 `scene model: xxx`。

**次可能场景（本次真实改进）**：存 top-2 到新列 `alt_place_name`
（阈值 0.12），相册列表/封面/场景筛选/全局搜索都按「主或次」命中。
效果：被误判成「病房」的房间照片，同时会出现在「育婴室/儿童房」等
更合理的次标签相册里，搜索次标签也能捞回来。老数据要重新识别才有 alt
（点一下场景重置即可，会全库重跑）。

## 六、2026-10-14 人脸聚类防误合（对应问题 5：gexuan 账号下"好多人混在一起"）

### 6.1 三个误合根因

| # | 病灶 | 证据 | 修复 |
|---|---|---|---|
| 1 | 没有"裕度"概念：只要 best >= req 就认领 | 两张不同人的脸都过阈值时，谁高一点就归谁 | `decideFaceAssignment()`：阈值 + 与第二名的裕度双重裁决 |
| 2 | ⭐**多样性因子方向反了** | 旧码 `return 0.6 + novelty * 0.8` ⇒ 越"不像近期样本"权重越大（最高 1.4） | 改为 `protoWeightFactor()`：越不像越**衰减**（最高 1.0，最大衰减 40%） |
| 3 | 二次合并无传递性约束 | A~B、B~C 各自够像就把 A/B/C 并成一组，跨身份串成大组 | `selectMergePairs()`：默认要求**互为最近邻**，且按 small→normal→strict 档位顺序取 |

第 2 条是主因：原型越"新奇"反而越容易被拉进来，等于主动往组里吸异类。

### 6.2 新增代码

- `src/workers/ai/faces/faceUtil.js`：四个纯函数
  `protoWeightFactor` / `pushTopRoot`（按 rootId 去重的 top-2）/ `decideFaceAssignment` /
  `selectMergePairs`（limit + 互为最近邻 + 三档位）
- `src/workers/ai/faces/faceWorker.js`：
  - `computeRecentDiversityFactor` 方向反转（改调 `protoWeightFactor`）
  - `findBestPrototype` 去掉 `confidentMargin` 的**提早返回**，改为全量扫描维护 top-2 后裁决
  - `secondaryMerge` 尾部三段贪心整体换成 `selectMergePairs`
- 单测：`node tool/_test_face_cluster_guards.js` ⇒ **26/26 PASS**，
  含"A~B~C 链只并 A~B"、"星型 hub 本轮一对一"、"103 作为桥不参与合并"等综合场景。

### 6.3 参数（`tableConfig`，改完需重启 worker）

| 键 | 默认 | 范围 | 含义 / 调法 |
|---|---|---|---|
| `ai_face_assign_margin` | 0.04 | 0~0.3 | 认领所需"与第二名的裕度"。**调大更保守**（不易误合，但同一个人可能被拆成两组）。gexuan 这种"混得很厉害"的账号建议 **0.08** |
| `FACE_SECOND_MERGE_MUTUAL`（环境变量） | 1 | 0/1 | 二次合并是否要求互为最近邻。**关掉会显著增加跨身份串并**，一般不要关 |
| `ai_face_second_merge_thresh` | 见 default | — | 二次合并原型阈值；调高更保守 |
| `ai_face_second_merge_best_sample_thresh` | 见 default | — | 二次合并"最佳样本"阈值；调高更保守 |

口径：**要减少误合就往上调阈值/裕度**，代价是同一个人可能裂成两组（裂开比混在一起好修 ——
裂开可以"合并人脸"，混了只能逐张移出）。

### 6.4 存量已经混在一起的人脸组怎么办

本次只修了"以后不再往里吸人"，**不会自动把已经混好的组拆开**。可选路径：

1. **最快（现在就能用）**：进人脸的相册页 → 多选混进来的照片 → 右下角「移出人脸相册」。
   这条路本轮已修好 —— 原先批量移出必定失败，根因是 `photoRouter` 裸引用注册导致
   方法内 `this._validPathsOf` 取不到（`this === undefined`），已把 `faceController` 的
   17 个被注册方法改成箭头函数类字段，批量移出/隐藏/合并一起恢复。
   移出后这些脸会在下轮重新聚类，按新决策层大概率归到正确的人。
2. **建议补的入口**：现在只有"移出"，缺"**把选中的照片移到另一个人物**"的**批量**版。
   服务端 `/face/photo/move`（`movePhotoToFace`）已经存在，只需要前端在人脸页多选态接一个
   "移动到…" + 人物选择器。这是修存量数据最省事的入口，建议优先补。
3. **全库重来（成本最高）**：`/face/reset` 清空人脸数据重跑。只在参数已调好、
   且错组遍布全库时才用。

### 6.5 未验证项（必须明确）

- 本轮的护栏只过了**单元测试**与 `node --check`；
  **没有**在真实库上跑过一次完整聚类做前后对比（没有"改前 vs 改后"的混组数量对照）。
  真实效果需要调高 `ai_face_assign_margin` 后跑一轮识别，
  看智能相册里"人脸"组的成员纯度与组数变化。
- `ai_face_assign_margin` 的建议值 0.08 是**保守方向的推荐**，不是实测扫出来的最优值。
